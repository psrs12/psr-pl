## Why

Corporate direction requires the personal loan acquisition platform to be rebuilt on this org's enterprise Go standards (see `CLAUDE.md`) — Go services, DynamoDB, Fargate/Step Functions/EventBridge — rather than the existing Java/Spring/Postgres/Kafka/Hexagonal implementation. The existing implementation (documented in the separate, untouched `psr-personal-loan` repository) remains the functional source of truth: this change preserves its service boundaries, domain behavior, and application lifecycle while replacing the technology stack and internal architecture style end to end.

## What Changes

- Introduce a five-service platform in `psr-pl`, mirroring the existing service boundaries with one deliberate deviation: `application-management-service`, `pricing-orchestration-service`, `offer-acceptance-service`, `document-service`, `compliance-orchestration-service`. `invitation-service` is not stood up as a standalone deployable — see the `invitation-service` decision below.
- Rebuild each service in Go using Handler → Service → Repository layering, packages organized by business capability, and small consumer-owned interfaces. **BREAKING**: drops Hexagonal ports-and-adapters as the internal architecture style.
- Replace Postgres-per-service with DynamoDB-per-service. **BREAKING**: relational/audit queries (e.g. compliance gate lookups) must be redesigned around access patterns and GSIs; no joins, no scans.
- Replace Spring Boot long-running JVM processes with Fargate/ECS containers per service; reserve Lambda for lightweight glue (validation, notifications, event handlers) per CLAUDE.md's Lambda-vs-Fargate guidance.
- Replace Kafka choreography with EventBridge (domain events) + Step Functions (central workflow orchestration). **BREAKING**: this is a behavioral shift from choreography (each service reacts independently) to orchestration (a Step Function centrally sequences the acquisition workflow, including the five compliance gates); event ownership and gate-sequencing rules need to be re-established under the new model.
- Define `application-management-service`'s acquisition-intake behavior in Go/DynamoDB terms:
  - Three application entry paths (invitation, direct, partner), with invitation-path name/address prefilled from the validated offer and non-editable; all other fields collected fresh on every path.
  - Email and phone are mandatory on all paths; a fixed set of applicant fields (employment, income, other income, rental expense, SSN, DOB, citizenship status) is required before submission regardless of path.
  - No draft/resume capability — the application is not persisted until submission (all-or-nothing, single session). No local cache of offer "in use" status is kept; checks against OfferLog are always live.
  - Application records support create, update, and retrieve only — no delete, to satisfy recordkeeping/adverse-action retention requirements.
  - Offer economics (term, amount, APR) are snapshotted onto the Application record at submission time as embedded attributes, since `pricing-orchestration-service` needs them later to honor the invited offer. Offer *status* (active/used) is never duplicated locally — OfferLog remains the sole source of truth, referenced from Application only by id.
  - A configurable inactivity-expiry sweep reverts an application's linked offer to `ACTIVE` in OfferLog when the applicant stalls after submission (exact lifecycle stage(s) monitored is an open design question, see design.md).
- **`invitation-service` is not a standalone service.** Its entire scope — retrieve/validate an offer from the external OfferLog system, and update the offer's status in OfferLog — is implemented as an internal adapter package inside `application-management-service`, since that is currently OfferLog's only consumer and the adapter owns no data of its own (OfferLog is the system of record for both offer content and offer status). If a second consumer of offer data emerges, extract this adapter into a standalone service at that point — the interface boundary (`OfferValidator` / `OfferStatusUpdater`) is already shaped for that extraction.
- **`pricing-orchestration-service` is Step-Functions-native, with one narrow REST API.** Per CLAUDE.md's own workflow diagram (`Persist Application → Start Step Function → Lambda → Lambda → Fargate → Lambda → Update Application Status`), pricing-orchestration's steps — soft pull, pricing calculation, offer selection, hard pull, decision routing — are implemented as individual Lambda functions (lightweight) and one Fargate task (pricing calculation, CPU-bound), invoked by a Step Functions state machine. `application-management-service` starts the execution on submission and stores the resulting `executionArn` on the Application record. **Revision to the original "no standalone API, ever" call**: the workflow must pause between pricing and hard pull so the applicant can select the offer and give explicit hard-pull consent (an FCRA requirement the fully-automated pipeline was originally missing entirely — no `CONSENT_CAPTURED`-equivalent gate existed). That pause uses Step Functions' `waitForTaskToken` pattern, and resuming it requires an API to receive the applicant's response — which now has two real consumers (the paused workflow step, and `pricing-offers-ui`), satisfying the same "standalone only if it owns data or has multiple consumers" rule that originally justified *not* building an API. The rest of the pipeline (soft pull, pricing, hard pull, decision) stays API-less.
- **`workflow-status-service` is a new capability, not present in the `psr-personal-loan` reference platform.** It exists so applicants can poll for status and next-steps after login without application-management-service needing to know anything about Step Functions: it queries the execution (`DescribeExecution`/`GetExecutionHistory`, looked up via an internal call to `application-management-service`) and translates the current state into a structured `{status, nextSteps[]}` response, richer than a bare status label.
- **`offer-acceptance-service`** now exists: declarations (fixed, placeholder disclosure content — not real legal text) and e-signature capture. E-signing requires every required declaration to be accepted (partial acceptance is rejected) and advances the application to `DOCUMENTS_REQUIRED` via `application-management-service`'s internal status-update endpoint — the same pattern `pricing-orchestration-service`'s decision step already uses.
- **`pricing-offers-ui`** now exists: the `<pricing-offer-selector>` web component `application-management-ui`'s `navigationConfig.js` already expected. Plain DOM/vanilla JS (no React), built as an IIFE via Vite, matching how the shell actually loads it (a `<script src>` tag registering a custom element, not an ES module import). Requires the applicant to explicitly check a hard-pull-consent box before the "Confirm" button will submit — client-side enforcement of the same consent gate the workflow enforces server-side.
- UI layer: `document-management-ui` remains out of scope (no corresponding service exists yet). `application-management-ui` **was** touched, despite the original intent to leave it alone — see "Impact" below.

## Capabilities

### New Capabilities
- `application-intake`: Applicant-facing application creation across invitation, direct, and partner entry paths — field requirements, prefill/editability rules, and submission gating, owned by `application-management-service`.
- `offer-lifecycle`: Offer validation, status transitions (active/used), and inactivity-driven reversion. OfferLog (external) is the system of record; the requirements in this capability constrain the internal OfferLog-adapter package inside `application-management-service`, not a standalone service.
- `platform-service-architecture`: Cross-cutting architectural requirements applying to the platform's services — Go layering, DynamoDB access-pattern design, Fargate/Lambda compute placement, and EventBridge/Step-Functions integration. Includes the general principle behind the `invitation-service`, `pricing-orchestration-service`, and offer-selection-API shape decisions: stand up a standalone deployable/API only when a capability owns persistent data or has multiple consumers.
- `pricing-orchestration`: Soft pull → pricing → applicant offer selection/consent → hard pull → decision, implemented as Step Functions-invoked Lambda/Fargate steps plus one narrow offer-selection REST API, owned by `pricing-orchestration-service`.
- `workflow-status`: Applicant-facing status/next-steps derived live from a Step Functions execution, owned by `workflow-status-service`.
- `offer-acceptance`: Declaration disclosure and e-signature capture, owned by `offer-acceptance-service`.

### Modified Capabilities
- None — no existing `openspec/specs/` capabilities exist in `psr-pl` yet; this change establishes the first ones.

## Impact

- **Affected systems**: `application-management-service` (extended: starts the pricing workflow on submission, exposes three internal endpoints — status update, execution lookup, session validate), `pricing-orchestration-service` (Lambda functions, one Fargate task, a Step Functions state machine, and now a narrow offer-selection REST API), `workflow-status-service` (standalone Fargate REST API), `offer-acceptance-service` (new: standalone Fargate REST API), `pricing-offers-ui` (new: standalone web component). No changes to `psr-personal-loan` (reference-only).
- **`application-management-ui` was modified**, despite the original "UI is out of scope" framing: a citizenship-status field was added (previously hardcoded and never actually collected, contradicting `application-intake`'s own required-field requirement), a bug was fixed where `monthlyObligations` was collected but silently dropped before being sent, the dead, contract-inconsistent `InvitePage.jsx` was removed, and its status polling was switched to `workflow-status-service`. These were corrections needed to make the already-built UI's real contract actually work against the services, not a redesign.
- **Affected infrastructure**: New DynamoDB table for `application-management-service` (`pl-application`); a Step Functions state machine and its Lambda functions + Fargate task + a new `pl-pricing-offer` DynamoDB table for `pricing-orchestration-service`; a Fargate service for `workflow-status-service` (no DynamoDB table of its own — see design.md); a new `pl-offer-acceptance` DynamoDB table and Fargate service for `offer-acceptance-service`. EventBridge is not yet used anywhere (all cross-service handoffs are direct HTTP/SDK calls — `StartExecution`, `SendTaskSuccess`, internal status-update endpoints).
- **Dependencies**: `application-management-service` depends on the external OfferLog system directly (via its internal adapter) and starts `pricing-orchestration-service`'s workflow at submission. `workflow-status-service` and `pricing-orchestration-service`'s offer-selection API both depend on `application-management-service` for session validation. `offer-acceptance-service` depends on `application-management-service`'s status-update endpoint. `pricing-offers-ui` depends on `pricing-orchestration-service`'s offer-selection API directly. `compliance-orchestration-service`'s five gates still depend on this same Step Functions orchestration model, not yet built.
- **Out of scope**: Any change to `psr-personal-loan`; `document-management-ui` and `document-service` (don't exist yet); `compliance-orchestration-service` (not yet built).
