## Context

`psr-personal-loan` (a separate, unmodified repository) documents a working personal loan acquisition platform: six Java/Spring Boot microservices, DDD + Hexagonal architecture, Postgres per service, Kafka choreography, a 15-state application lifecycle, and five compliance gates. That repository is the functional reference and stays untouched — it is someone's own architecture, not something this change alters.

Corporate direction requires a parallel, independent rebuild in `psr-pl` on this org's enterprise Go standards (`CLAUDE.md`): Go, DynamoDB, Fargate/Lambda, EventBridge/Step Functions, Handler→Service→Repository layering instead of Hexagonal. Service boundaries, applicant-facing behavior, and the lifecycle must be preserved; the internal architecture and infrastructure are being deliberately replaced.

This design covers the platform-wide architectural mapping and the one capability explored in depth so far, `application-management-service`'s intake flow. The other four standalone services keep their documented responsibilities but are not designed in detail here — that is follow-on work.

## Goals / Non-Goals

**Goals:**
- Map each of the five standalone existing services to a Go/DynamoDB/Fargate implementation with equivalent external behavior (APIs, lifecycle states, compliance gates).
- Replace Kafka choreography with EventBridge + Step Functions, explicitly designing how the five compliance gates get sequenced under central orchestration instead of independent reaction.
- Fully specify `application-management-service`'s intake behavior: entry paths, field/prefill rules, persistence model, and its interaction with the external OfferLog system (via an internal adapter) for offer validation and status transitions.

**Non-Goals:**
- Changing anything in `psr-personal-loan`.
- Redesigning the UI layer. (`application-management-ui` did need small corrections to make its existing, already-built contract actually work — see the proposal's Impact section — but that's fixing bugs against an established contract, not redesigning it. `pricing-offers-ui`/`document-management-ui` are genuinely untouched, since no corresponding backend exists yet.)
- Detailed DynamoDB table/GSI design for `offer-acceptance-service`, `document-service`, or `compliance-orchestration-service` — captured as open questions/follow-on work, not designed here.
- Consolidating services into a single deployable. `application-management-service` and `workflow-status-service` remain independently deployed Go/Fargate services; CLAUDE.md's `internal/` package-by-capability example happens to name-match the existing capabilities but is not a signal to merge them.
- Standing up `invitation-service` as a deployable, or giving `pricing-orchestration-service` a standalone REST API — see the decisions below.

## Decisions

**Five services, not six, not a monolith.** Each of `application-management-service`, `pricing-orchestration-service`, `offer-acceptance-service`, `document-service`, and `compliance-orchestration-service` becomes its own Go module/deployable on Fargate/ECS, each with Handler→Service→Repository layering and its own DynamoDB table(s). Rejected alternative: a single Go modular monolith using CLAUDE.md's `internal/<capability>` layout — tempting because the package names coincidentally match the service list, but rejected because it would merge independently-scaled, independently-owned deployables and contradicts "keep all microservices intact."

**`invitation-service` is not stood up as a standalone deployable.** Its documented responsibility — retrieve/validate an offer and update its status — is entirely a facade over the external OfferLog system: it owns no data of its own (OfferLog is system of record for both offer content and status), and `application-management-service` is currently its only consumer. Standing up a separate Fargate task, DynamoDB table, and deployment pipeline for a two-call proxy contradicts CLAUDE.md's "avoid unnecessary abstractions." Instead, this is implemented as an internal adapter package (`OfferValidator` / `OfferStatusUpdater`) inside `application-management-service`. Rejected alternative: build it standalone to match the reference platform's service list exactly — rejected because preserving service boundaries is valuable where a service owns data or has multiple consumers, neither of which holds here; matching the org chart isn't a reason on its own. Extraction trigger: the moment a second service needs to read or write offer data directly, pull this adapter out into its own service — the interface boundary is already shaped for that.

**EventBridge + Step Functions replace Kafka choreography.** Cross-service domain events (e.g., "application submitted", "decision made") move to EventBridge. The acquisition workflow's sequencing — today implicit in which events each service chooses to consume — becomes an explicit Step Functions state machine that orchestrates: submission → compliance Gate 1 (AML pre-screen) → soft pull → pricing → Gate 2 (FCRA consent) → hard pull → decision → (approval path: documents → Gate 4 TILA audit → e-sign → Gate 5 pre-funding AML → funding) or (decline path: Gate 3 adverse action). Rejected alternative: keep Kafka running alongside the AWS-native stack — rejected because CLAUDE.md's AWS service list doesn't include Kafka and running two messaging backbones adds operational surface for no clear benefit once the platform is Go/AWS-native anyway.

**DynamoDB per service, access-pattern-driven.** Each service owns its own table(s); no shared/global table across services (preserves the "per-service data ownership" property Postgres-per-service had). Rejected alternative: one shared single-table design across all six services — rejected because it would blur the service ownership boundaries CLAUDE.md and the existing platform both treat as inviolable.

**Fargate for the services themselves; Lambda for glue.** Each of the six services runs as a long-running Fargate/ECS task behind the API layer, since they are synchronous REST APIs equivalent to today's always-on Spring Boot services. Lambda is reserved for short-lived, event-triggered work: the inactivity-expiry sweep, notification sends, lightweight validation steps invoked from Step Functions.

**`application-management-service` persists Application only, never Offer status.**
- Application supports create, update, retrieve — no delete (recordkeeping/adverse-action retention).
- Nothing is persisted pre-submission: the intake flow is stateless/single-session until submit, so there is no draft state to clean up and no local record to check for "offer already in use" — that check always calls OfferLog live via the internal adapter.
- At submission, offer economics (term, amount, APR, and the offer/invitation/customer-reference id) are snapshotted as embedded attributes on the Application item — needed later by `pricing-orchestration-service` to honor the invited offer, and simple to model since nothing else independently updates those attributes.
- Offer *status* is deliberately never stored on Application, even as a cache — OfferLog is the sole source of truth, always queried live, to avoid the two-sources-of-truth drift that a cached status field would introduce (e.g., an expiry sweep flips the canonical status but a stale local copy doesn't). Application only carries a reference id. Status transitions are driven through a small consumer-owned interface (`OfferStatusUpdater`) called from `application-management-service` at defined trigger points: mark `USED` on submission; revert to `ACTIVE` on the inactivity-expiry sweep.

**Invitation-path identity binding.** Name and address are sourced from the validated offer and rendered non-editable specifically to bind the applicant to the invited identity — an editable name/address on the invitation path would defeat the purpose of requiring an invitation at all. This applies only to the invitation path; direct and partner paths collect and allow editing of every field.

**Offer-validation failure degrades gracefully.** An invalid/expired/already-used offer does not hard-stop the applicant — they continue on the direct-application path instead, re-entering any fields the offer would otherwise have prefilled.

**`pricing-orchestration-service` is Step-Functions-native, with one narrow exception.** Its steps (soft pull, pricing calculation, hard pull, decision routing) are implemented as individual Lambda functions plus one Fargate task (pricing calculation — CPU-bound per CLAUDE.md's Fargate-usage guidance), invoked directly by a Step Functions state machine, with no always-on API in front of them. This matches CLAUDE.md's own workflow diagram literally (`Start Step Function → Lambda → Lambda → Fargate → Lambda → Update Application Status`) and reflects that this capability is inherently multi-step background processing, not a synchronous request/response API the way `application-management-service` is. `application-management-service` calls `StartExecution` directly after persisting the Application (immediate, not event-mediated — matches the diagram's direct arrow rather than introducing EventBridge indirection for something with exactly one producer and one workflow to start), storing the returned `executionArn` on the Application record. The Fargate pricing-calculation task uses Step Functions' `ecs:runTask.waitForTaskToken` integration (not `.sync`, which has no return-value channel) — the container computes the result and reports it back via `SendTaskSuccess`/`SendTaskFailure`. Rejected alternative: a standalone REST service like `application-management-service`, invoked as a single Step Functions task — rejected because it would collapse four independently-reasoned-about steps into one opaque call, losing the per-step visibility `workflow-status-service` depends on (current-state-in-history only means something if each step is its own state).

**The offer-selection API is the one deliberate exception to "no standalone API."** Building `pricing-offers-ui` surfaced a real gap: the original pipeline went straight from pricing to hard pull with no pause for the applicant to select an offer or give hard-pull consent — and no `CONSENT_CAPTURED`-equivalent gate existed at all, which is an FCRA compliance gap, not just a missing UI screen. Fixed by inserting an `AwaitOfferSelection` state using `lambda:invoke.waitForTaskToken`: a small Lambda (`present-offer-lambda`) stores the task token and priced offer (via this new API's internal endpoint) without resuming the execution itself; the execution stays paused until `pricing-offers-ui` calls `POST .../selected-offer/confirm`, which resumes it via `SendTaskSuccess`. A `ConsentGivenCheck` Choice state then branches: consent false or absent routes to a `ConsentDeclined` Pass state (decision=DECLINED, reason="applicant did not give hard-pull consent") rather than proceeding to `HardPullRequest` — there is no path in this state machine where a hard pull can run without recorded consent. This API now has two real consumers (the paused workflow step, and `pricing-offers-ui`), which is exactly the condition that was previously used to justify *not* building an API for this service — the condition changed, so the decision changed with it, rather than being treated as sacred. It owns one small DynamoDB table (`pl-pricing-offer`: applicationId, offer economics, task token, status, consent) — genuinely new state this service didn't need before, since a paused execution's resume token has to live somewhere retrievable between the Lambda that captures it and the API call that uses it.

**The offer-selection API requires session authentication — this was missed on first pass and caught by live verification, not code review.** Every other applicant-facing endpoint in this platform validates a session token against `application-management-service`; the offer-selection `GET`/`POST` endpoints initially didn't, which would have let anyone who knew an `applicationId` view or confirm someone else's loan offer. Found by actually testing with no token and a garbage token before assuming the happy path was the whole story, and fixed with the same `SessionValidator` → `application-management-service`'s internal `/internal/sessions/validate` pattern `workflow-status-service` already uses.

**Confirm resumes the workflow before persisting CONFIRMED, not after.** First implementation did it the other way around (mark confirmed, then attempt the Step Functions resume) — found via live testing, not inspection: a resume failure (e.g. a stale/fabricated task token) left the record permanently marked CONFIRMED with no way to retry, because the second attempt hit the already-confirmed check first. Reordered so a failed resume leaves the record at `PENDING_SELECTION`, retryable. Regression-tested with a fake resumer that fails on the first call and succeeds on retry.

**Workflow input is deliberately minimal — financial figures only, no PII.** The Step Functions execution payload carries `applicationId`, `requestedAmountCents`, `requestedTermMonths`, `annualIncomeCents`, `monthlyObligationsCents` — no name, SSN, DOB, or address. This directly addresses the risk flagged earlier in this document about Step Functions execution history retention: since that risk was accepted as "fine for economics, not for SSN-grade PII," the payload was designed from the start to only ever contain the former.

**`workflow-status-service` is a new, standalone service — not folded into `application-management-service`.** Unlike the `invitation-service` decision, this one does meet the "stand up a service" bar: it has a genuinely different concern (translating live Step Functions execution state into applicant-facing status) that would otherwise couple `application-management-service` to Step Functions API details it doesn't otherwise need to know about, and it's plausible other consumers (e.g. an ops dashboard) want the same translated view later. It owns no DynamoDB table of its own — the `applicationId → executionArn` mapping lives on `application-management-service`'s Application record (fetched via a new internal endpoint) rather than being duplicated, following the same "no duplicated source of truth" principle used for offer status. Session validation is likewise never re-implemented here — every status request is authenticated via a call back to `application-management-service`'s session store, since that's where session ownership already lives.

**`offer-acceptance-service` is standalone, and genuinely owns data.** Unlike the offer-selection API, this one was never a close call: it owns its own persistent record (the e-sign event itself — who signed what, when) and is the natural, sole owner of declaration content. E-signing is create-only (no update, no delete — a signature is immutable once made) and requires every required declaration to be accepted; partial acceptance is rejected outright rather than silently proceeding. On success it advances the application to `DOCUMENTS_REQUIRED` via the same internal status-update endpoint pattern `pricing-orchestration-service`'s decision step uses, rather than inventing a new integration style. Declaration content itself is a placeholder (not real legal/compliance-reviewed text) — structurally correct, not production copy, same caveat as the pricing/credit-scoring formulas.

**`pricing-offers-ui` is vanilla JS, not React.** `application-management-ui` is React; this component isn't, because mounting a full React tree inside a custom element that a *different* app loads via a bare `<script>` tag (not a bundler-aware import) adds real complexity — shadow DOM boundaries, React root lifecycle tied to `connectedCallback`/`disconnectedCallback`, bundle size for a component that's a handful of fields and two buttons. Hand-rolled DOM manipulation in a `HTMLElement` subclass avoids all of that for something this small. Built with Vite's library mode outputting a single IIFE (`pricing-offer-selector.iife.js`), matching exactly how `application-management-ui`'s `useWebComponentScript` hook already expected to load it (a plain script tag registering a custom element, not an ES module). Consent is enforced client-side (the confirm button is a no-op with a visible error until the checkbox is checked) as well as server-side in the state machine's `ConsentGivenCheck` — the client-side check is a UX nicety, not the actual gate; a request that somehow bypassed the UI still can't skip consent, because the workflow branches on the server-recorded value, not anything the client claims.

## Risks / Trade-offs

- [Choreography → orchestration is a behavioral change, not a swap] Centralizing sequencing in Step Functions changes failure/retry semantics for the five compliance gates and puts sequencing ownership in one place instead of each gate enforcing its own trigger conditions. → Design the Step Function's gate sequencing explicitly as part of `compliance-orchestration-service`'s own design pass (flagged as open question below); do not assume today's Kafka consumer logic ports over unchanged.
- [DynamoDB access-pattern redesign for audit/compliance queries] Relational queries like "all applications currently in `COMPLIANCE_HOLD`" have no direct DynamoDB equivalent without deliberate GSI design. → Treat this as required design work for `compliance-orchestration-service`, not an implementation detail to improvise later.
- [Live OfferLog dependency during intake] Every offer-in-use check and status transition is a live call, with no local fallback/cache by design. → Acceptable given OfferLog is the sole source of truth by design; if this becomes an availability concern, revisit as a deliberate trade-off change, not a workaround bolted onto `application-management-service`.
- [Folding the OfferLog adapter into `application-management-service` couples its release cycle to a second consumer's needs] If `pricing-orchestration-service` later needs offer data, its access is mediated through `application-management-service` (or the adapter must be extracted first) rather than calling OfferLog directly. → Treat "second consumer appears" as the explicit trigger to extract the adapter into its own service before wiring that second consumer up, not something to defer indefinitely.
- [Embedded offer attributes vs. separate item] Snapshotting offer economics as embedded attributes assumes no future need to independently update just the offer portion of an Application item. → If that assumption breaks (e.g., pricing needs to write back adjusted terms), revisit splitting into a separate item under the same partition key.
- [`workflow-status-service` availability is coupled to `application-management-service`] Every status request makes two internal HTTP calls to `application-management-service` (session validate, execution lookup) before it can even reach Step Functions. → Accepted for now since it avoids duplicating session/execution-mapping state; revisit if this round-trip becomes a measured latency problem, not preemptively.
- [Real Lambda execution verified via Floci; Fargate/ECS still not] A second local emulator, Floci (a LocalStack-compatible, single-endpoint AWS emulator — see floci.io), was tried as a replacement for the separate DynamoDB Local / Step Functions Local containers. Its Lambda emulation is genuinely real and Docker-backed: `soft-pull-lambda` etc. were cross-compiled, packaged, deployed as real Lambda functions, and invoked directly (`aws lambda invoke`) with correct results, confirmed via `docker ps` showing a real container running AWS's own `public.ecr.aws/lambda/provided:al2023` runtime image. Its ECS/Fargate emulation was not equally real in this test: `run-task` reported `RUNNING` for `pricing-fargate`'s task definition, but no container ever appeared in `docker ps` — a shallow/fake response, not real execution (possibly gated behind a paid tier; the health check reported `"edition":"community"`, unconfirmed against Floci's pricing). → Fargate/ECS execution (the pricing-calculation step) is still unverified by anything. Do not assume Floci's `RUNNING` status means a task actually ran, in this or future exploration.
- [Floci's Step Functions Lambda-invoke integration does not wrap responses the way real AWS does] Real AWS Step Functions' `arn:aws:states:::lambda:invoke` integration wraps a Lambda's return value in `{"Payload": ..., "StatusCode": ...}`; our ASL's `ResultSelector` (`$.Payload.score`) is written for that shape. Floci instead returns the Lambda's raw return value directly as the task result with no `Payload` wrapper, confirmed by isolating a single-state test state machine — so running our actual `definition.asl.json` against Floci produces `null` values for every `ResultSelector`-mapped field, even though the underlying Lambda invocation succeeded. → This is a Floci compatibility gap, not a bug in the ASL (which targets real AWS behavior). Do not "fix" the ASL to match Floci's unwrapped shape — that would break it on real AWS. If Floci is used for future local runs of this exact state machine, either strip `ResultSelector` for local-only testing or wait for Floci to match AWS's wrapping.
- [No end-to-end Fargate execution verified anywhere] Between Step Functions Local (mock-config feature didn't engage) and Floci (ECS/Fargate appears shallow), neither local emulator has verified the pricing-calculation Fargate task actually running inside a full state-machine execution. Lambda steps now have real-execution evidence (via Floci, direct invoke); the Fargate step does not. → Treat a real AWS (or a working local ECS/Fargate emulation) dry run of the Fargate step specifically as still required before considering `pricing-orchestration-service` done.
- [Confirm's resume-then-persist ordering has a smaller residual gap] Reordering Confirm to resume the workflow before persisting CONFIRMED (see the decision above) fixes the worse failure mode, but doesn't eliminate the underlying two-write problem: if `SendTaskSuccess` genuinely succeeds but the subsequent DynamoDB `Update` then fails, the real Step Functions execution has moved on to `HardPullRequest` while this service's own record still shows `PENDING_SELECTION`. → Accepted as a smaller, harder-to-avoid inconsistency than the one that was fixed (worst case here is a stale display, not an unconfirmable/unretryable record); revisit only if this proves to matter in practice, e.g. by having `workflow-status-service`'s live execution-state view be treated as authoritative over this service's own stored status for display purposes.
- [Real end-to-end offer-selection resume never verified] The `waitForTaskToken` pause/resume was verified in two disconnected halves — the offer-selection API's `Confirm` logic against a *fabricated* task token (correctly fails, correctly stays retryable), and the state machine's control flow only via ASL review, not execution — because producing a real paused `AwaitOfferSelection` execution requires a real `SoftPullRequest` → `PricingCalculation` run first, which hits the same unresolved Fargate-execution gap above. → Once Fargate execution is verified (previous item), extend that verification through a real pause-and-resume at `AwaitOfferSelection`, not just the two halves in isolation.

## Migration Plan

Not applicable in the traditional sense — `psr-pl` is a new, independent codebase; there is no live system to migrate off of, and `psr-personal-loan` is not being decommissioned or cut over. Rollout is standard net-new service delivery (build, deploy, cut traffic to `psr-pl` when each service is ready), sequenced service-by-service starting with `application-management-service` since the other four depend on its behavior.

## Open Questions

- Which lifecycle stage(s) does the inactivity-expiry sweep actually watch (e.g. `DOCUMENTS_REQUIRED`, `OFFER_ACCEPTED` awaiting e-sign, both, others)? Not yet decided.
- Does withdrawal or decline (in addition to expiry) also revert the linked offer to `ACTIVE` in OfferLog, or only expiry?
- Does `compliance-orchestration-service`'s gate logic live inside the Step Function definition itself, or inside the service (invoked as a task from the Step Function)?
- GSI/access-pattern design for `compliance-orchestration-service`'s audit and status-lookup queries is unstarted.
- DynamoDB and event-schema design for `document-service` has not been explored yet.
- The pricing/decision logic in `pricing-orchestration-service` (credit score simulation, APR tiering, affordability capping) is explicitly a placeholder — no real credit bureau or underwriting engine integration exists.
- `offer-acceptance-service`'s declaration content (TILA disclosure, e-sign consent, arbitration agreement) is placeholder text, not real legal/compliance-reviewed copy.
- EventBridge is not yet used anywhere in the built services — every cross-service handoff so far is a direct HTTP/SDK call (`StartExecution`, `SendTaskSuccess`, internal status-update endpoints). Whether EventBridge is introduced for a future handoff (e.g., `document-service` onward) or direct calls continue to suffice is unresolved.
- Whether declining the offer (vs. declining consent) should be distinguished is unresolved — `pricing-offers-ui`'s "Decline This Offer" button currently sends the same `consentGiven: false` as an unchecked consent box would, both routing to the same `ConsentDeclined` state with the same generic reason text.
- `pl-audit` (the immutable audit-event table CLAUDE.md's DynamoDB rules carve out) is not yet designed or implemented for `application-management-service` — what events it captures, write pattern, and retention are still open. Deliberately deferred, not an oversight.
